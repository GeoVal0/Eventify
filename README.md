## 1 Overview
Eventify is an event management and online booking system built for the course assignment, consisting of a React frontend and a FastAPI backend. Three roles are supported end-to-end: attendee, organizer, and admin, each with a distinct set of capabilities enforced both in the UI and by the API. For the full endpoint-by-endpoint contract (request/response shapes, auth requirements), see `API_CONTRACT.md` at the root folder.

## 2 Backend
FastAPI + SQLAlchemy + SQLite REST API for the assignment. For the full endpoint-by-endpoint contract (request/response shapes, auth requirements), see `API_CONTRACT.md` at the root folder.

### 2.1 Setup
```bash
cd backend
python3 -m venv venv
source venv/bin/activate # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 2.2 Running
```bash
uvicorn main:app --reload --ssl-keyfile key.pem --ssl-certfile cert.pem
```
The API is now at `https://localhost:8000`. Interactive docs (Swagger UI, auto-generated by FastAPI from the code) are at `https://localhost:8000/docs`. A SQLite file `tedi.db` is created automatically on first run in the `backend/` directory.

#### 2.2.1 Built-in Admin Account
Seeded automatically on first startup (assignment requirement: an admin account must exist out of the box):
* **username:** `admin`
* **password:** `admin123`

Override via environment variables before starting the server:
```bash
export ADMIN_USERNAME=myadmin
export ADMIN_PASSWORD=a-real-password
```
Also set `JWT_SECRET_KEY` to something private for anything beyond local dev. It defaults to a placeholder value in `auth.py`.

#### 2.2.2 Running over HTTPS (SSL/TLS)
The assignment requires all interactions to be SSL/TLS encrypted. The frontend already has this covered for its own dev server via `@vitejs/plugin-basic-ssl` (see `vite.config.js`). To match on the backend:
```bash
sh generate_dev_cert.sh # one-time: creates key.pem + cert.pem for localhost
uvicorn main:app --reload --ssl-keyfile key.pem --ssl-certfile cert.pem
```
The API is then at `https://localhost:8000`. Your browser will warn about the self-signed certificate the first time, that's expected for local development. `key.pem`/`cert.pem` are per-machine and already gitignored as each developer generates their own.

#### 2.2.3 CORS
`main.py` allows `https://localhost:5173`. Vite's default dev port is `5173`.

### 2.3 Design Decisions
* Registration role is restricted server-side to ATTENDEE / ORGANIZER only. ADMIN cannot be self-registered because it only exists via the seeded account.
* `ticket_type_id` is globally unique in the DB (EV1024-T1), not scoped per event, because it's a single primary-key column. The DTD only requires uniqueness within one event, so the XML/JSON export strips the event-id prefix back down to the DTD's local form (T1) (see `crud._local_ticket_type_id`).
* Booking availability is enforced with a single atomic SQL `UPDATE WHERE available >= N`, not a read-then-write check, so two simultaneous bookings for the last seat can't both succeed. This was verified under genuine concurrent load (10 simultaneous requests against 2 remaining seats -> exactly 2 succeeded, 8 got a clean 409, availability never went negative).
* Messaging is scoped to an organizer-attendee pair that shares a booking on the relevant event (`crud.verify_messaging_relationship`).
* The recommender trains fresh on every request rather than being cached/scheduled, since it's fast enough at realistic scale (~130ms with ~16 users/16 events/112 interactions) for this project.
* The recommender's `n_factors` scales down automatically on very small/sparse data (`crud.get_recommendations`), because a fixed large factor count is underdetermined on a handful of interactions; many different parameter settings fit tiny training data equally well without generalizing the same way. Testing at toy scale (3 users per preference group) showed real unreliability that scaling up to a realistic size (8 users per group) resolved cleanly, matching the proven-reliable result from `recommender_demo.py`.

### 2.4 Development Process
The backend was developed independently of the frontend at the start of the assignment, split into the following steps.

#### 2.4.1 Step 1: Data Model & API Contract
This step established the relational schema as SQLAlchemy models and defined the full REST API surface up front. Work began by writing `API_CONTRACT.md` before touching most of the actual endpoint code, so the frontend could be built against a stable interface without needing to wait for the backend to be finished first.

#### 2.4.2 Step 2: Auth & RBAC
Implemented user registration with admin approval, login via JWT (chosen for simplicity), and a built-in admin account, along with the permission system distinguishing guest, attendee, organizer, and admin access throughout the API. Role checking was split into a reusable `require_role(...)` factory rather than one function per role, and registration deliberately rejects role: "ADMIN" server-side for security.

#### 2.4.3 Step 3: Events CRUD & Capacity Validation
Built full CRUD for events, along with the ticket-type system and the rule that ticket quantities can never exceed an event's total capacity. Covers the event lifecycle (draft -> published -> cancelled) and the constraints on when an event can be edited, cancelled, or removed entirely.

#### 2.4.4 Step 4: Search & Browsing
Added public event discovery: filtering by category, free-text search across title and description, date range, price range, and location, with paginated results.

#### 2.4.5 Step 5: Booking System
Implemented ticket booking for attendees, including real-time availability checks and safe handling of simultaneous booking attempts for the same limited stock.

#### 2.4.6 Step 6: Messaging
Added a messaging system between organizers and attendees who share a booking, including inbox and sent views, read/unread tracking, message deletion, and automatic notifications to all affected attendees when an event is cancelled.

#### 2.4.7 Step 7: Data Export
Implemented administrator-only export of all event data in both XML and JSON format. Covers every event regardless of status, with nested ticket type, booking, and media information included in the output.

#### 2.4.8 Step 8: Recommendation Engine
Implemented the Biased Matrix Factorization recommendation algorithm from scratch using plain numpy, trained on each attendee's booking and viewing history to suggest relevant events. Covers model training, cold-start handling for new users, and validation of the algorithm's correctness against both synthetic data and the provided dataset.

## 3 Frontend

### 3.1 Tech Stack
* **React** (function components, hooks) with Vite as the build tool/dev server (default dev port `5173`).
* **React Router** (`react-router-dom`) for client-side routing and role-gated navigation.
* **MUI** (Material UI) for the component library and styling (`sx` prop, theming via a shared `AppTheme`).
* **React Leaflet** + OpenStreetMap tiles for the event-location map shown on multiple pages across the system.
* Plain fetch-based API layer (`src/api.js`), no additional HTTP client library.
* Auth state via React Context (`AuthContext`), backed by a JWT stored in localStorage.

### 3.2 Prerequisites
* Node.js and npm.
* The Eventify backend running (see section 2), by default expected at `https://localhost:8000` (see `API_BASE_URL` in `src/api.js`). The frontend will not function meaningfully without it since there is no mock mode.

### 3.3 Getting Started
1. Start the backend first (section 2).
2. Then start the frontend dev server:
   ```bash
   npm run dev
   ```
3. Open `https://localhost:5173` in a browser.

#### 3.3.1 Configuration
The backend base URL is currently a constant (`API_BASE_URL`) at the top of `src/api.js`, defaulting to `https://localhost:8000`.

### 3.5 Routing & Roles
Role gating happens in `NavBar.jsx`: attempting to reach an organizer or admin-only route while unauthenticated redirects to login with the intended destination preserved via router state (`location.state.from`), so `Login.jsx` can send the user back to where they were headed after a successful sign-in. Attempting to reach a route for the wrong role forces a logout first, so the person can sign in again as the correct account.

| Route | Role | Purpose |
| --- | --- | --- |
| `/Home` | any | Landing page |
| `/login` | any | Sign in |
| `/sign-up/*` | any | Registration (attendee / organizer) |
| `/search/SearchEvents` | any | Browse/filter events |
| `/search/BookTickets` | attendee | Event detail booking |
| `/messages` | authenticated | Inbox/sent/compose |
| `/organizer/NewEvent` | organizer | Create event |
| `/organizer/EditEvent` | organizer | Edit event, manage photos |
| `/organizer/EventHistory` | organizer | List own events |
| `/organizer/ViewEvent` | organizer | Event detail, attendees, cancel |
| `/admin/UserList` | admin | Pending/approved users |
| `/admin/UserDetails` | admin | Approve/reject a user |

### 3.6 Feature Notes

#### 3.6.1 Messaging
Reachable at `/messages` and via the floating mail-icon badge which is visible in the entire system when logged in (unread count, polled periodically). Organized into Εισερχόμενα (Inbox), Απεσταλμένα (Sent), and Νέο (Compose). Compose mode is detected from data rather than a role flag: whichever of "has bookings" / "organizes events" actually returns results decides whether the "as attendee" or "as organizer" compose flow (or a toggle between both) is offered. Messaging is scoped to an existing booking relationship for a specific event. On event cancellation, the organizer's cancellation action triggers a broadcast message to every attendee who booked that event.

#### 3.6.2 Recommendations
The "Προτάσεις Για Εσάς / Δημοφιλείς Εκδηλώσεις" carousel on the Home page calls the backend's Biased Matrix Factorization endpoint for logged-in attendees. It falls back to a plain event list (unlabeled as personalized) for guests, organizers, and admins, since the recommendation endpoint is attendee-only. The heading itself reflects the backend's own `cold_start` flag, distinguishing a genuinely personalized ranking from a popularity fallback for new users. With a small number of events/accounts, the personalization signal can be weak relative to raw popularity. This is an expected property of collaborative filtering on sparse data, not a defect; see section 2.3 for how this is validated independently of live-data sparsity.

#### 3.6.3 Category System
Event categories are a fixed set of codes (`music`, `theater`, `cinema`, `sports`, `arts`, `festival`, `seminar`) selected from a dropdown at event creation/edit time. The underlying code is used everywhere data actually needs to match (image lookup, search filtering, recommendation).

#### 3.6.4 Admin Data Export
Available from `NavBar.jsx`'s ΔΙΑΧΕΙΡΙΣΤΗΣ menu: exports every event as XML (matching the DTD) or JSON, admin-only, triggered as a direct file download (see also section 2.4.7).
